# 项目结构与命名规范

## 命名

- Python 模块使用小写英文与下划线，例如 `cloud_documents.py`、`tk_bd_metrics.py`。
- 同一业务使用统一前缀：`business_analysis_*`、`tk_*`、`test_*`。
- Python 类名使用 PascalCase，函数与变量使用 snake_case；不为统一外观改动数据库字段或外部 API 字段。
- 不在源码文件名中使用空格、日期、最终版、备份等后缀。历史材料放入明确的归档目录。
- 修改现有文件时遵循其周边格式；不对大型业务文件做全量自动格式化，避免掩盖业务修改。

## 整理边界

- 主站目前依赖大量根目录模块，不能只移动文件而不更新导入、模板路径、Docker COPY 和测试路径。
- `bjc.py` 是多模块依赖的数据库辅助层，不是无用文件；本轮保留，后续可单独迁移到基础设施包。
- `图片/`、`无限画布/`、`VideoClaw/` 等已有独立项目或子模块，保留现有路径，避免破坏构建和挂载。
- 有效测试保留；仅删除确认完全重复或已废弃的临时测试。不以“生产没有引用测试”为删除依据。
- `tmp/` 中存在历史已跟踪文件；`.gitignore` 不会自动取消跟踪。逐项核对后清理，不直接删除整个目录。
- 配置密钥、生产数据库、上传图片、生成结果、运行状态与日志不属于格式整理范围。

## 后续迁移顺序

1. 为单个业务建立包，迁移其模块并更新所有引用。
2. 保持对外路由及权限检查不变，运行该业务和部署回归测试。
3. 验证 Docker 构建及静态资源路径后，再处理下一个业务。

这是一轮保守整理，不代表所有历史模块已经完成包结构迁移或全量格式化。

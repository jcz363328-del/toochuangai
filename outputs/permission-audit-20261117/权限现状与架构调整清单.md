# 公司架构调整：权限现状与待确认清单

盘点日期：2026-11-17。来源：当前运行容器连接的数据库，只读查询 dbo.quanxian 与 dbo.UserPermissionOverrides；部门名称来自本地代码映射，并非最新飞书通讯录。未修改任何授权或组织数据。

数据库共 110 条功能记录，其中启用或未设置状态 110 条；个人覆盖 4 条；代码部门映射 38 个。

## 需要先确认的规则

- 运行时功能授权读取数据库；代码中的默认名单和种子脚本不代表当前实际授权。原《项目权限清单.md》日期为 2026-07-18，不宜作为本次迁移依据。
- 个人单独授权/禁用优先于部门和常规个人名单；例外必须逐项确认是否保留。
- 部门白名单与个人白名单任一命中即可获得直接权限；all 等表示所有已登录用户。
- * 是全功能授权记录，必须优先复核其人员和部门。
- 子功能可以反向点亮父级入口；拥有父级入口不会自动获得所有子功能。
- 代码中部门树继承根为“运营部”“内容生产工厂”，排除“新人组”；调整父子关系时需复核继承。
- 部门名称存在硬编码映射；部门改名但 ID 不变时，也需要刷新名称及缓存。
- 功能权限与数据范围分开核对；亚马逊补货按运营人员与店铺映射限制，TikTok、联营看板、经营分析需分别复核。

## 新架构确认顺序

1. 填写《部门新旧对应待确认.csv》：确认改名、合并、拆分、撤销及新上级和负责人。
2. 对照《功能权限现状.csv》逐项确认新部门、角色、查看/编辑/导出权限；空白代表待确认，不代表撤权。
3. 逐项确认《个人权限例外.csv》的授权与禁用是否继续保留，同时核对功能表中的个人白名单。
4. 核对店铺负责人、本人/本部门/指定店铺/全公司数据范围，明确调岗后的旧数据访问权限。
5. 先输出迁移差异及回退脚本，选普通员工、负责人、跨部门人员验证，再应用调整。
